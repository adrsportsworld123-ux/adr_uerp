## What this is

The Next.js back-office admin app for the Universal Retail & Wholesale ERP — the UI surface for functions the Flutter POS app (`../erp-pos-flutter`) deliberately doesn't cover, because it's the cashier terminal, not back-office tooling. Talks to `erp-core-go`'s `/api/v1` REST API (`../erp-core-go`) — the same Bearer-token contract the Flutter app uses, not a separate backend.

**This repo existed only as a name in `docs/tech_stack_decision.md` (in `erp-core-go`) until it was actually created** — Phase 0's own Definition of Done called for "a Next.js admin showing a login screen," and was marked done without it ever being built. Read `../erp-core-go/docs/tech_stack_decision.md` §10 and `../erp-core-go/docs/phased_roadmap.md` before assuming anything about scope here — those documents are the source of truth for what this app is supposed to own, not this file's memory of a particular session.

## Stack

Next.js 16 (App Router, Turbopack), React 19, TypeScript, Tailwind CSS v4 (CSS-based config — no `tailwind.config.ts`, see `app/globals.css`), shadcn/ui components built on **Base UI** (`@base-ui/react`), not Radix — component APIs differ from older shadcn docs (no `asChild` on `Button`; use `buttonVariants()` + a plain `<Link>` instead; `Select`'s `onValueChange` is `(value: string | null) => void`, not `(value: string) => void`). Playwright for E2E (`e2e/`), matching what `tech_stack_decision.md` already named for this app.

**Next.js 16 is genuinely new** — it ships its own warning (`AGENTS.md`, auto-regenerated by `next dev`, safe to commit) that training-data assumptions about Next.js conventions may be stale. Check `node_modules/next/dist/docs/` or the actual generated boilerplate before assuming an API surface, the way `LayoutProps<"/">` (auto-generated route types) replaced the classic `{ children: React.ReactNode }` layout prop pattern.

## Auth model

Bearer token in `localStorage` (`lib/auth.tsx`), not a cookie/session — deliberately consistent with how the Flutter POS app authenticates against the same backend, not a second pattern. `useRequireAuth()` is a client-side redirect guard, not middleware (middleware would need the token in a cookie). Session restore-from-localStorage happens in a `useEffect` post-mount, not a lazy `useState` initializer — this app is server-rendered first, so reading `localStorage` during render would either crash (no `window`) or cause a hydration mismatch.

## Current state

**Built and verified** (real browser via Playwright against a live `erp-core-go` + Postgres, not mocked — see `e2e/`):
- Login (`/login`) — closes the Phase 0 gap above
- Suppliers: list + create
- Purchase: GRN (create draft → add line via barcode lookup → complete), Bills (create against a completed GRN → record payments), Returns (create with accumulated lines)
- Accounting: Chart of Accounts (list + create custom account), manual Journal Entry (dynamic line builder with client-side balance check), Party Ledger (supplier only — see gap below), Day Book, Cash Book
- Multi-Branch: Branches (list + create), Branch Transfers (request with barcode-driven line entry → status-driven detail page covering Approve/Reject → Dispatch → Complete-with-optional-discrepancy → Cancel) — `e2e/multi-branch.spec.ts` logs in as three different sessions in sequence (POS User denied approval, Branch Manager approves, POS User dispatches/completes) to verify the permission gate isn't just a UI-level disabled button
- Pricing: product/variant browse with margin/markup display (`GET /products` — the catalog-browse endpoint this app needed and that endpoint's very first real caller), a cost-plus/target-margin calculator, single-variant editing with the negative-margin block→override flow, and bulk update (preview → apply, no category/brand filter in the UI yet even though the API supports one) — `e2e/pricing.spec.ts` runs as Branch Manager since `pricing.manage` is permission-gated
- Product Search (`/search`): free-text, typo-tolerant catalog search backed by the new `internal/search`/OpenSearch service (`GET /products/search`) — debounced query box plus min/max price filters, a "search unavailable" fallback state when OpenSearch is down rather than a crash, and a per-row link into `/pricing` for edits — `e2e/search.spec.ts` verifies an exact match, a deliberately typo'd query still fuzzy-matching, and a price filter correctly excluding a result
- Customers (`/customers`, Phase 3's first sub-area): search/filter list with VIP/Regular/New/Dormant segment badges, a registration form (`/customers/new`) with a B2C/B2B toggle that conditionally requires a GSTIN, and a detail page (`/customers/[id]`) with inline profile editing and consolidated cross-branch purchase history — `e2e/customers.spec.ts` covers B2C registration, a B2B registration blocked client-side without a GSTIN then succeeding with one, and search-by-phone
- Promotions & Loyalty (`/promotions`, Phase 3's second sub-area): promotion CRUD (percent/fixed/BOGO/volume/min_value, with a product picker sourced from `GET /products` but no category picker — same raw-ID gap as Party Ledger's customer field, see below), coupon CRUD, and a loyalty settings form (earn rate/redeem rate/rolling expiry) — all gated by `promotions.manage`/`loyalty.manage`, so writes are attempted and surfaced as a form/toast error on `403` rather than hidden client-side (same pattern Pricing's `pricing.manage` already established). Deliberately CRUD/config only: applying a promotion/coupon/redemption to a live sale is a POS-terminal action (`erp-pos-flutter`), not this app's job — same boundary Pricing already draws (edits prices here, a sale picks them up automatically). A customer's loyalty balance/ledger is shown read-only on their own detail page (`/customers/[id]`) instead, since it's customer-scoped state, not merchant-wide config. `e2e/promotions.spec.ts` covers promotion/coupon creation and deactivation, a POS User denied writing (permission gate), and — since this app has no cart/checkout UI to earn points through — seeds one real finalized sale via a direct API call (bypassing the browser) to verify the customer detail page's loyalty section renders what that sale actually produced.
- Notifications (`/notifications`, Phase 3's third and last sub-area): the sent-notification audit log (`GET /notifications` — the first endpoint in this app whose *read*, not just its writes, is permission-gated by `notifications.view`; a denied user sees the API's own permission message the same way any other `403` surfaces here, not a blank page) plus low-stock reorder-point configuration (`PATCH /inventory/reorder-point`, gated by `inventory.adjust`) since this app has no general Inventory screen yet to put that on instead. No "resend receipt" button here — that belongs next to a specific order's own detail view once one exists in this app, not a standalone admin form. `e2e/notifications.spec.ts` seeds a real finalized sale via a direct API call (same pattern as Promotions & Loyalty's own test) to verify the log shows a real receipt notification, sets a reorder point end-to-end with the resulting stock levels displayed, and confirms a POS User sees the permission-denied message on the log but can still look up stock (unlike saving a reorder point, which is denied).
- Credit (Phase 4's first sub-area, added to `/customers/[id]` rather than its own route — it's customer-scoped state, same reasoning Loyalty's section on that page already established): credit limit/payment terms/credit hold settings (gated by `credit.manage`, attempted-and-toast-erred on `403` same as every other gated write in this app), outstanding balance, an aging breakdown (current/0-30/30-60/60-90/90+), and a per-invoice "record payment" action (not gated, mirroring `POST /purchase/bills/{id}/payments`'s own precedent). No "make a credit sale" control — that's the POS terminal's job, the same boundary this app draws for Pricing and Promotions & Loyalty. `e2e/credit.spec.ts` seeds a real credit sale via a direct API call, verifies the outstanding balance renders, edits credit settings through the UI as Branch Manager, confirms a POS User is denied that same edit but can still view the card, and records a payment through the UI that correctly clears the open invoice.
- GST Returns (`/gst`, Phase 4's second sub-area): a viewer, not a filer — the merchant still uploads the export to the GST portal themselves. Shows GSTR-3B and GSTR-1's computed summaries, a reconciliation badge (computed tax vs. the ledger's own GST Payable balance), GSTR-1's named list of gaps in the export (rendered as-is from the API, not paraphrased), and a collapsible raw-JSON panel per return with a copy-to-clipboard button. Not permission-gated on the backend (matches the rest of `internal/accounting`'s reports), so no denial path to cover. `e2e/gst.spec.ts` confirms both returns render against this repo's own real prior test data, the JSON panel expands with real content, and a period with no data shows empty (₹0.00) totals rather than an error.
- Bank Reconciliation (`/bank-reconciliation`, Phase 4's third sub-area): the first file-upload UI in this app (`<input type="file">` + `FileReader`, no library needed) — imports a CSV bank statement, shows per-line match status with an inline near-miss candidate picker for manual matching, and a date-ranged reconciliation report (matched total, unmatched statement lines, unmatched ledger entries). Import/match/unmatch are gated by `bank_reconciliation.manage`, attempted-and-toast-erred on `403` same as every other gated write in this app; reads are open. `e2e/bank-reconciliation.spec.ts` seeds a real ledger entry via a direct API call, uploads a real CSV file from disk (Playwright needs an actual file for `setInputFiles`, unlike the JSON bodies this suite's other specs hand `request` directly), confirms it auto-matches, then unmatches and re-matches it manually through the candidate picker, checks the reconciliation report reflects it, and confirms a POS User is denied importing.
- Cash Reconciliation (`/cash-reconciliation`, Phase 4's fourth sub-area, reconciliation type #1 of `pos_frd_complete.md` §16's four): a denomination-grid EOD count against that date's real cash sales (fetched live from the existing EOD Cash report), with variance/approval-needed computed **client-side** as the cashier types, so the reason/approver fields only appear once actually needed rather than a submit-then-retry round trip. No route-level permission gate here (unlike every other gated screen in this app) — approval is an inline PIN check against whichever user ID is entered, mirroring how the backend already authorizes a manual sales discount; `authorized_by` is a raw user-id text input, the same documented gap Party Ledger's customer field already has. `e2e/cash-reconciliation.spec.ts` uses far-past dates (guaranteed-zero real sales data, so the math is fully deterministic) to verify a zero-variance count auto-closes with no approval box, a variance shows the box and rejects a wrong PIN, the correct PIN succeeds, and history reflects both.

**Known gaps, not yet closed:**
- **`SEED_BRANCH_ID` is still hardcoded** in `lib/api-client.ts` for the *POS-flow-adjacent* screens (purchase GRN/returns still assume one branch, matching the Flutter app's own `main.dart` simplification) even though a real branch picker is now possible — `GET /branches` exists and the Branches/Transfers screens already use it properly. Worth threading a proper branch selector into the Purchase screens too, not just Multi-Branch's own.
- **GRN, purchase-return, and transfer line entry still resolve a variant via barcode lookup** (`GET /products/barcode/{code}`), not the newer `GET /products/search`. Fine for a barcode-driven retail catalog, awkward for typing a SKU from memory — worth switching those three screens to the search endpoint now that it exists.
- **The Search screen has no category/brand filter UI** (same underlying gap as Pricing's bulk-update form below) — there's still no `GET /categories`/`GET /brands` list endpoint to populate a picker from, so both screens are limited to free-text/price filtering.
- **The Pricing screen's bulk-update form has no category/brand/price-range filter UI** even though `POST /pricing/bulk-update/*` accepts one — it always sends an empty filter (every product).
- **The Party Ledger screen's "customer" option still requires pasting a raw customer ID** even though `GET /customers` now exists — worth wiring a proper customer picker in now that the endpoint is there. No credit-sale flow exists yet that would actually populate a customer ledger, though (see `erp-core-go`'s CLAUDE.md/roadmap for that gap).

## Working conventions to keep

- Money/quantity fields from the API are strings end-to-end (never parsed to `number` for arithmetic, only for `<input type="number">` values going the other direction) — same reasoning as `erp-pos-flutter`'s API client: the server already settled them to `NUMERIC(14,2)`-correct values, and round-tripping through a JS `number` would reintroduce float rounding risk for zero benefit.
- `lib/types.ts` mirrors `erp-core-go`'s JSON response shapes by hand — there's no shared schema/codegen between the two repos (consistent with `erp-core-go` itself not using an ORM/codegen layer yet — see that repo's `tech_stack_decision.md` §3.1 as-built note).
- Run `npm run lint && npx tsc --noEmit` before considering anything done. The one standing exception is `react-hooks/set-state-in-effect` in `lib/auth.tsx`'s session-restore effect — see the comment there for why it's a deliberate, justified suppression, not a lint config gap to "fix" by removing the effect.
- `npx playwright test` needs `erp-core-go`'s docker-compose stack running on `:8080` with the seed user's password set (`POST /dev/set-password`, `DEV_AUTH_TOOLS_ENABLED=true` — dev-only, see that repo's docs) — it hits the real API, not a mock. Playwright's own bundled Chromium download may be blocked by network egress in a sandboxed environment; `playwright.config.ts` uses `channel: "chrome"` (the system install) specifically to route around that.
