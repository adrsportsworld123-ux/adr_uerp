# erp-web-admin — context for Claude Code

This file is read automatically by Claude Code at the start of every session in this repo.

## What this is

The Next.js back-office admin app for the Universal Retail & Wholesale ERP — the UI surface for functions the Flutter POS app (`../erp-pos-flutter`) deliberately doesn't cover, because it's the cashier terminal, not back-office tooling. Talks to `erp-core-go`'s `/api/v1` REST API (`../erp-core-go`) — the same Bearer-token contract the Flutter app uses, not a separate backend.

**This repo existed only as a name in `docs/tech_stack_decision.md` (in `erp-core-go`) until it was actually created** — Phase 0's own Definition of Done called for "a Next.js admin showing a login screen," and was marked done without it ever being built. Read `../erp-core-go/docs/tech_stack_decision.md` §10 and `../erp-core-go/docs/phased_roadmap.md` before assuming anything about scope here — those documents are the source of truth for what this app is supposed to own, not this file's memory of a particular session.

## Stack

Next.js 16 (App Router, Turbopack), React 19, TypeScript, Tailwind CSS v4 (CSS-based config — no `tailwind.config.ts`, see `app/globals.css`), shadcn/ui components built on **Base UI** (`@base-ui/react`), not Radix — component APIs differ from older shadcn docs (no `asChild` on `Button`; use `buttonVariants()` + a plain `<Link>` instead; `Select`'s `onValueChange` is `(value: string | null) => void`, not `(value: string) => void`). Playwright for E2E (`e2e/`), matching what `tech_stack_decision.md` already named for this app.

**Next.js 16 is genuinely new** — it ships its own warning (`AGENTS.md`, auto-regenerated by `next dev`, safe to commit) that training-data assumptions about Next.js conventions may be stale. Check `node_modules/next/dist/docs/` or the actual generated boilerplate before assuming an API surface, the way `LayoutProps<"/">` (auto-generated route types) replaced the classic `{ children: React.ReactNode }` layout prop pattern.

## Auth model

Bearer token in `localStorage` (`lib/auth.tsx`), not a cookie/session — deliberately consistent with how the Flutter POS app authenticates against the same backend, not a second pattern. `useRequireAuth()` is a client-side redirect guard, not middleware (middleware would need the token in a cookie). Session restore-from-localStorage happens in a `useEffect` post-mount, not a lazy `useState` initializer — this app is server-rendered first, so reading `localStorage` during render would either crash (no `window`) or cause a hydration mismatch. **Session expiry** (`lib/api-client.ts` "Session lifecycle" block, driven by `AuthProvider`): silent `POST /auth/refresh` while the user is active; back to `/login` with a reason after a full role-tier inactivity window or a rejected refresh, returning to the same page after re-login. Don't "simplify" this into refresh-on-every-401 — that would turn the FRD's 15-minute inactivity timeout into the refresh token's 30 days. See `../erp-core-go/docs/phase0_1_design.md` §3.29.

## Working conventions to keep

- **Choosing a product, variant, category or brand is always a typeahead** (2026-10-11, `erp-core-go` `phase0_1_design.md` §3.49): `ProductPicker` (`components/data/product-picker.tsx`, server search; `mode="product"` for a whole-product choice) or `SearchSelect` (`components/data/search-select.tsx`, an in-memory list such as categories, brands or branches). Never a dropdown filled from `GET /products?limit=200`: that silently hid everything past the first page. Line-entry screens (GRN, purchase returns, transfers) offer search and barcode side by side.
- **Finance pages share one layout** (2026-10-18). Every page has a `PageHeader` with a one-line description and its actions (Print / PDF, New …). Controls that choose what a page shows go in a `FilterBar` of labelled `Field`s, and sections go in a `Panel` (all in `components/data/panel.tsx`). Money is formatted with `rupees()` in right-aligned `tabular` cells, and ledger sides with `drCr()`. Statuses and sources are `StatusChip`s, labelled with `SOURCE_LABEL`/`METHOD_LABEL`, never raw codes or `Badge`. Voucher stages use `VOUCHER_TONE`. Default dates come from `localDate()`, not `toISOString()`, which gives the UTC day before 05:30 IST. Branches come from `BranchSelect` plus `useMyBranches()` (`components/data/branch-select.tsx`), which starts on the user's own branch (`homeBranchId` from `/me/permissions`). Day Book, Cash Book and Cash Reconciliation used to be pinned to `SEED_BRANCH_ID`, and Cash Reconciliation's history took a typed branch UUID. Book totals (Day Book, Cash Book) come from the server (`erp-core-go` `phase0_1_design.md` §3.64); never sum money strings in the browser. A sale's e-invoice and e-way bill are on `/sales/{id}` (`components/sales/einvoice-documents.tsx`), and `/e-invoicing` is the lookup by order ID. Report pages are `max-w-5xl`, detail pages `max-w-4xl`, settings `max-w-2xl`, and lists are full width.
- **CRUD screens** follow the Promotions/Price Rules pattern: a list with search and a status filter, create and edit in one dialog (`Modal`, submit button tied to the form with `form=`), activate/deactivate on the row, and delete through `DeleteWithDependencies` (or a confirmation), disabled with the reason when the API would refuse.
- **Monitoring screens refresh themselves**: `useLiveRefresh` plus `useServerList().refresh` (a background re-fetch that doesn't dim the rows), as on the Sales page.
- Money/quantity fields from the API are strings end-to-end (never parsed to `number` for arithmetic, only for `<input type="number">` values going the other direction) — same reasoning as `erp-pos-flutter`'s API client: the server already settled them to `NUMERIC(14,2)`-correct values, and round-tripping through a JS `number` would reintroduce float rounding risk for zero benefit.
- `lib/types.ts` mirrors `erp-core-go`'s JSON response shapes by hand — there's no shared schema/codegen between the two repos (consistent with `erp-core-go` itself not using an ORM/codegen layer yet — see that repo's `tech_stack_decision.md` §3.1 as-built note).
- Run `npm run lint && npx tsc --noEmit` before considering anything done. The one standing exception is `react-hooks/set-state-in-effect` in `lib/auth.tsx`'s session-restore effect — see the comment there for why it's a deliberate, justified suppression, not a lint config gap to "fix" by removing the effect.
- `npx playwright test` needs `erp-core-go`'s docker-compose stack running on `:8080` with the seed user's password set (`POST /dev/set-password`, `DEV_AUTH_TOOLS_ENABLED=true` — dev-only, see that repo's docs) — it hits the real API, not a mock. Playwright's own bundled Chromium download may be blocked by network egress in a sandboxed environment; `playwright.config.ts` uses `channel: "chrome"` (the system install) specifically to route around that.
